> **핵심 주장** — **AI 에이전트가 실험·제조 장비를 다루게 하려면, 먼저 제각각인 장비를 "읽고 쓸 수 있는 상태의 묶음"으로 통일하는 드라이버 표준이 필요합니다.** 그 위에서 에이전트는 장비를 매 스텝 직접 제어하지 않습니다. 탐색으로 배운 것을 **결정론적 코드로 굳혀 장비에 넘기고**, 자신은 판단과 예외 처리를 맡습니다.

---

## 들어가며

**MCP가 LLM과 소프트웨어 도구 사이의 연결을 표준화했다면, Model Hardware Standard(MHS)는 같은 일을 물리 장비에 대해 하려 합니다.** 현미경, 리퀴드 핸들러, 로봇팔 같은 실험·제조 장비를 AI 에이전트가 발견하고, 이해하고, 안전하게 조작하게 하는 공유 규격입니다. Anthropic은 2026년 8월 27일 이를 일부 연구소와 첨단 제조사에 리서치 프리뷰로 열었고, 안전성 평가를 마친 뒤 오픈소스로 공개할 계획이라고 밝혔습니다. 특정 모델에 묶이지 않으며(model-agnostic), 어떤 에이전트 하네스든 MCP 같은 표준 프로토콜로 접근할 수 있습니다.

MHS는 Anthropic Beneficial Deployments 팀의 Alek Kemeny와 HHMI Janelia의 포닥 Arco Bast의 협업에서 시작되었습니다. 발표는 Anthropic의 본문과, 파트너 6곳(Genentech, UW Baker/Pinglay Labs, CMU, HHMI Janelia, QuEra, Tetsuwan)이 직접 쓴 사례 보고로 이루어져 있습니다. 논문이 아니므로 통제된 비교 실험은 없고, 결과는 사례 보고로 읽어야 합니다. 또한 스펙 문서가 아직 공개되지 않아, 이 글의 아키텍처 설명은 발표문과 사례에서 재구성한 것입니다.

아래에서는 발표의 논지를 따라가면서, 실험 자동화와 장비 제어 쪽 개념은 필요한 자리에서 함께 설명합니다.

## 1. 문제 — 장비들은 서로 말을 하지 않는다

### 1.1 파편화의 실제

**CMU 사례가 문제를 가장 선명하게 보여줍니다.** 연속 희석 용량-반응 실험에 필요한 장비 넷이 PC 세 대에 흩어져 있고, 제어 방식이 모두 다릅니다.

| 장비 | 제어 방식 |
|---|---|
| 로봇팔 | 정상적인 API 없음. 스케줄러가 감시하는 폴더에 XML 작업 파일을 떨어뜨려야 함 |
| 리퀴드 핸들러 | 구형 Windows ActiveX/COM 스크립팅만 지원하고, 최신 SDK 없음 |
| 플레이트 리더 | 프로그래밍 인터페이스가 아예 없음. 화면 GUI뿐 |

HHMI Janelia의 2광자 현미경 리그도 비슷합니다. 검출기는 MATLAB, 카메라는 Python, 전기생리 장비는 C#으로 돌아갑니다. 스테이지 두 개가 서로의 위치를 알아야 시료의 절대 위치를 알 수 있는데, 한 프로그램이 가진 값을 다른 프로그램은 모르기 때문에 신호를 물리적으로 중계하려고 DAQ 보드를 하나 더 붙이기도 합니다. 실험 하나를 시작하려면 프로그램 7개를 정해진 순서대로 띄워야 하고, 순서를 틀리면 세션 전체를 날립니다.

**그 결과 장비 통합에는 수 주에서 수 개월이 걸리고, 자동화는 한 프로토콜을 엄청나게 반복할 때만 수지가 맞습니다.** UW 필자의 대비가 정확합니다. 공장 라인이 한 프로토콜을 만 번 돌린다면, 연구실은 1년에 수십 개 프로토콜을 돌리고 그중 절반이 새것입니다.

여기에 AI 에이전트를 얹으면 문제가 하나 더 생깁니다. 장비를 연결해 놓더라도 그 데이터를 에이전트와 공유할 공통 방법이 없고, 에이전트가 장비를 안전하게 조작할 공통 방법도 없습니다.

### 1.2 그래서 이 발표가 던지는 질문

> 장비 쪽에 표준 하나를 깔면, 통합과 운용을 AI 에이전트가 맡을 수 있을까요?

이 질문에 답하려면 네 개의 벽을 넘어야 합니다. 이후의 각 절은 이 네 벽을 하나씩 살펴보고, MHS가 각 벽을 어떻게 넘는지 다룹니다.

**⛔ 벽 1 — 인터페이스 파편화** 장비마다 언어, 프로토콜, 제어 방식이 다릅니다.

**⛔ 벽 2 — 코드에 없는 지식** 로봇팔의 무게처럼 조작에 꼭 필요한 정보가 종이 매뉴얼이나 사람의 암묵지에만 있습니다.

**⛔ 벽 3 — 안전** 명령이 실물을 움직입니다. 실패하면 대물렌즈가 충돌하거나, 레이저 출력이 과해 시료가 표백됩니다.

**⛔ 벽 4 — 시간척도** 장비는 에이전트의 온라인 추론보다 빨리 돌아야 할 때가 있습니다.

---

## 2. 배경 — 벽을 정확히 보기 위한 두 가지 도구

### 2.1 통합 비용의 산수 (벽 1)

장비 쌍마다 전용 브리지를 짜는 방식과, 표준에 한 번씩만 맞추는 방식을 비교하면 다음과 같습니다.

$$C_{\text{p2p}}(N) = \binom{N}{2} = \frac{N(N-1)}{2}\qquad\longrightarrow\qquad C_{\text{std}}(N) = N$$

- $N$: 장비 수
- $C_{\text{p2p}}$: 장비 쌍마다 bespoke 브리지를 짜야 하는 최악의 경우의 통합 비용
- $C_{\text{std}}$: 각 장비를 표준에 한 번씩만 맞추는 경우의 통합 비용

**에이전트 쪽까지 포함하면 $M$개 에이전트 하네스 × $N$개 장비의 조합이 $M+N$으로 줄어듭니다.** MCP가 소프트웨어 도구에 대해 적용했던 논리와 똑같고, 이름(Model Context Protocol ↔ Model Hardware Standard)도 짝을 이룹니다. Janelia 필자가 "통합 비용이 더 이상 장비 수에 따라 늘지 않는다"고 쓴 것이 바로 이 식의 효과입니다.

### 2.2 시간척도의 층위 (벽 4)

벽 4를 이해하려면 장비 제어에 여러 속도의 루프가 겹쳐 있다는 점을 먼저 봐야 합니다.

| 층 | 전형적 주기 | 사례 |
|---|---|---|
| 장비 내부 서보 루프 | µs–ms | QuEra 레이저 lock의 PID 서보 |
| 결정론적 스크립트 | 초 | QuEra 복구 스크립트 0.9–14초 |
| 에이전트 판단 | 스텝당 수 초~수십 초 (필자 추정) | 파라미터 선택, 곡선 해석 |
| 실험 라운드 | 분~시간 | CMU 분주 1회 4–5분, UW PCR 판 교체 90분 |

**에이전트가 매 스텝 추론하며 루프 안에 들어갈 수 있는 곳은 사실상 맨 아래 층뿐입니다.** 로봇 쪽의 "느린 계획 + 빠른 제어" 계층과 같은 구조의 문제입니다.

## 3. 방법 — 벽 하나에 장치 하나

MHS의 구성 요소는 네 벽에 하나씩 대응합니다.

```
  scientist / engineer  (natural-language goal)
          |
          v
  +--------------------------------+
  |  AI agent (any model/harness)  |   slow: plan, interpret, decide
  +--------------------------------+
       |           |            |
      MCP         CLI      code files (API)       <- wall 4
       |           |            |
       v           v            v
  +--------------------------------+
  |  MHS driver layer              |
  |   - primitives: read / write   |   <- wall 1
  |   - discovery                  |   <- wall 1
  |   - reference file (from tags) |   <- wall 2
  |   - enforced safety limits     |   <- wall 3
  +--------------------------------+
       |           |            |
     [arm]   [liquid handler] [plate reader] ...
   file-drop    COM/ActiveX      GUI only
```

### 3.1 벽 1 → 표준 드라이버: 모든 장비를 "상태의 묶음"으로 본다

MHS 드라이버의 명령 체계는 단순합니다. 기본 프리미티브는 `read`(예: 온도 읽기)와 `write`(예: 온도 설정) 둘입니다. 각 장비는 표준 포맷으로 자신을 알리므로(discovery), 중간에 전용 "번역기" 없이 네트워크 너머의 장비와 에이전트가 서로를 찾을 수 있습니다. CMU는 이를 "상태(state)와 절차(procedure)의 매니페스트"라고 표현하였습니다. 사례들을 하나로 묶으면 장비 하나를 다음 3-튜플로 볼 수 있습니다(필자의 정리이며, 발표문이 이 형식을 제시하지는 않았습니다).

$$\mathcal{D}_i = (\mathcal{S}_i,\ \mathcal{P}_i,\ \mathcal{R}_i)$$

- $\mathcal{D}_i$: $i$번째 장비
- $\mathcal{S}_i$: 상태 변수 집합. 예: 온도, "3번 위치에 플레이트 있음", "웰 채워짐". `read`로 읽고, 쓰기 가능한 변수는 `write`로 설정합니다
- $\mathcal{P}_i$: 절차 집합. 예: aspirate, shake
- $\mathcal{R}_i$: 레퍼런스 정보(3.2절). 측정 가능 항목, 조정 가능 항목, 안전 한계

**Janelia의 구현이 이 모델의 원형입니다.** 모든 장비의 변수, 제어값, 센서값이 **공유 메모리 위의 딕셔너리 하나**에 들어갑니다. 공유 메모리는 OS가 여러 프로그램의 동시 접근을 허용하는 메모리 영역이므로, 어떤 언어로 짠 프로세스든 여기에 붙어 읽고 쓸 수 있습니다. 분석은 "슬롯(딕셔너리 항목)에서 읽기 → 재사용 가능한 변환 → 다른 슬롯에 쓰기"의 사슬로 짜입니다. MHS 자체가 리그 전체의 상태를 공유 메모리의 표준 딕셔너리에 올린다는 Arco Bast의 이 아이디어에서 자라났습니다.

다만 여기서 의문이 생깁니다. `read`와 `write` 두 동사만으로 로봇팔이나 현미경 같은 복잡한 장비를 정말 표현할 수 있을까요?

> ### 💡 동사를 줄이고 명사(상태)를 늘린다 — REST와 같은 설계
>
> **REST가 GET/PUT 몇 개의 동사와 무수한 리소스로 웹을 표현하듯, MHS는 read/write와 상태 딕셔너리로 장비를 표현합니다.** 장비의 복잡도는 동사 대신 **상태 공간과 절차 목록**이 흡수합니다.
>
> 이 선택의 이득은 코드 재사용의 단위가 바뀐다는 데 있습니다. Janelia 필자는 뷰어를 장비별로 따로 만들지 않고 **데이터 타입별**(이미지, 시계열, 스펙트럼)로 한 번씩만 작성하였습니다. 카메라로 잰 심박의 스펙트럼을 계산하는 변환 코드를, 다른 언어로 돌아가는 다른 장비의 신경 활동 데이터에 그대로 재사용하였습니다.
>
> 어댑터 아래에는 무엇이 있어도 됩니다.
>
> - **CMU** — 폴더 감시 스케줄러가 제출 파일 하나당 만드는 결과 파일 두 개를 하나로 합칩니다(보통 1초 이내). COM 메서드는 벤더 문서를 보거나 Claude 에이전트가 인터페이스를 탐색해 알아냈습니다. GUI만 있는 리더는 사람처럼 화면을 조작합니다.
> - **Tetsuwan** — 벤더 지원이 없어서 장비마다 SBC(single-board computer)를 커넥터로 붙였고, 기존 스케줄러와 드라이버 스택을 MHS 명령으로 전부 대체하였습니다.

### 3.2 벽 2 → 자연어 태그에서 레퍼런스 파일로

**코드만 봐서는 알 수 없는 장비 특성이 있습니다.** 발표문이 든 예는 로봇팔의 무게입니다. 안전하게 다루려면 알아야 하지만, 이런 정보는 지금까지 종이 매뉴얼이나 사용자 PC 어딘가, 혹은 사람의 암묵지로만 존재했습니다.

MHS 드라이버에는 이런 정보를 자연어로 적는 **태그**가 있습니다. 사용자가 직접 적어도 되고, 에이전트가 사용자를 인터뷰해 채워도 됩니다. 드라이버는 이 태그로부터 **레퍼런스 파일**을 자동 생성합니다. 장비가 무엇을 측정하는지, 무엇을 조정할 수 있는지, 어떤 안전 한계가 강제되는지가 여기에 담기고, 에이전트는 이 파일만으로 처음 보는 장비를 다룰 수 있습니다.

LLM 배경에서 보면 이것은 MCP 도구 설명(docstring)의 물리 버전입니다. 즉, 이 장치는 물리 지식을 **텍스트로 주입하는 통로**이고, 뒤집어 말하면 여기에 적히지 않은 물리는 에이전트가 모릅니다. 이 한계가 실제로 드러나는 장면은 5.3절의 Genentech 사례에서 다룹니다.

### 3.3 벽 3 → 안전: 드라이버가 강제하는 한계

레퍼런스 파일에는 강제될 안전 한계가 들어갑니다. Janelia 필자는 MHS가 장비 수준에서 한계를 강제하기 때문에, 에이전트가 레이저 출력을 실수로 과하게 올려 시료를 표백시킬까 걱정하지 않아도 된다고 밝혔습니다. CMU는 고장 상황 6가지(플레이트 없음, 플레이트 회전, 리더 사용 중, 카메라 연결 끊김, 장비 응답 없음, 비상정지 활성)를 일부러 만들었는데, 시스템은 **어떤 장비도 움직이기 전에** 6가지를 모두 차단하였습니다.

그렇다면 한 가지 의문이 생깁니다. 에이전트가 충분히 똑똑하다면, 안전 판단도 에이전트에게 맡기면 되지 않을까요?

> ### 💡 안전은 에이전트의 판단이 아니라 드라이버의 불변식이다
>
> **확률적 정책 위에 결정론적 가드를 두는 구조이므로, 에이전트가 틀려도 하드 층이 사고를 막습니다.** 사례들을 모아 보면 안전 장치가 세 층으로 쌓여 있습니다.
>
> | 층 | 성격 | 사례 |
> |---|---|---|
> | 하드 (드라이버) | 에이전트가 무엇을 명령하든 넘을 수 없는 한계와 선행조건 | Janelia 레이저 출력 한계, CMU 고장 6종 사전 차단, 전송 전 카메라로 플레이트 존재·방향 확인 |
> | 소프트 (에이전트) | 위험해 보이면 멈추고 확인을 요청 | QuEra: 조금만 위험해 보여도 승인을 기다려 실험이 밤새 멈추기도 함 |
> | 사람 승인 | 제안 → 승인 → 실행 | Tetsuwan: Slack으로 복구 절차를 제안하고, 승인되면 실행 |
>
> LLM 쪽 비유로는 프롬프트에 "조심해"라고 적는 것과 도구 서버에 권한을 거는 것의 차이입니다.

### 3.4 벽 4 → 세 가지 제어 경로와 "코드로 굳히기"

에이전트가 장비를 제어하는 경로는 **MCP, CLI, 코드 파일(API)** 세 가지이고, 셋을 조합하면 한 줄의 코드로 여러 장비를 오케스트레이션할 수 있습니다. 평소에는 에이전트가 장비의 운용 데이터를 받아 단계를 배열하고, 결과를 감시하고, 조건이 바뀌면 파라미터를 조정합니다.

**작업이 길거나 에이전트의 온라인 추론보다 빨리 돌아야 하면, 에이전트는 여러 장비의 드라이버 명령을 코드 파일로 체이닝합니다.** 이렇게 하면 장비는 매 스텝 에이전트의 추론 없이 스스로 돌아갑니다.

발표문의 레이저 정렬 예가 이 흐름을 잘 보여줍니다. Claude는 레이저를 조금 조정하고 카메라로 빔이 어떻게 움직였는지 관찰하는 과정을 반복하며 인과를 파악하였습니다. 그다음 배운 것을 결정론적 스크립트로 묶어, 이후에는 명령 하나로 정렬이 끝나게 만들었습니다.

```
  phase A: explore (agent in the loop)      phase B: exploit (agent out)
  -------------------------------------     ----------------------------
    act --> observe --> reason                deterministic script
     ^                     |                  runs at device speed
     +---------------------+                  single command
                |                                     ^
                +------- write code file -------------+
```

- **phase A** — 에이전트가 루프 안에서 조작·관찰·추론을 반복하며 장비의 거동을 파악합니다
- **phase B** — 파악한 내용을 코드로 굳혀, 에이전트 없이 장비 속도로 실행합니다

그렇다면 에이전트가 매 스텝을 추론하지 않는 동안, 에이전트의 역할은 무엇일까요?

> ### 💡 에이전트는 제어기가 아니라 제어기를 짜는 쪽이다
>
> QuEra 사례가 이 구도의 극단입니다(5.2절). 역할이 다른 Claude 인스턴스 4개가 루프를 돌았습니다. 하나는 가설을 세우고, 하나는 복구 스크립트를 고치고, 하나는 실제 레이저에서 실행하며 로그를 남기고, 하나는 로그를 읽고 다음 변경을 정합니다. 이 순환이 밤새 수백 번 반복되었고, 최종 산출물은 **에이전트 없이 프로덕션에서 도는, 사람이 읽을 수 있는 결정론적 스크립트**입니다.
>
> 반대로 PID 튜닝은 온도와 압력에 따라 파라미터가 표류하므로 에이전트를 루프에 남겨둡니다. **코드로 굳힐지 에이전트를 남길지는 대상이 얼마나 변하는지(비정상성)가 결정합니다.**
>
> Tetsuwan도 같은 철학입니다. LLM은 제안만 하고, 의미를 보존하는 재작성 규칙으로 이루어진 결정론적 컴파일러가 정확성을 보장합니다.
>
> Agentic AI 쪽에서 보면, 도구를 매번 호출하는 대신 스크립트를 써서 돌리는 code-as-action의 선택과 같습니다. 로봇 쪽에서는 LLM이 제어 코드를 생성하는 code-as-policy 계열과 같은 계보입니다. 얻는 것은 두 가지로, 탐색 비용은 한 번만 내고 실행은 싸게 반복할 수 있으며, 런타임 산출물을 사람이 감사할 수 있습니다.

## 4. 왜 작동하는가

**⓵ 통합 비용이 장비 수에 비례하지 않습니다.** 2.1절의 산수가 실제로 나타납니다. Janelia에서 새 카메라를 붙이는 데 수 분이 걸렸고, 카메라가 잡은 빔 위치를 곧바로 빔 조향 미러에 되먹여 정렬 정밀도를 높였습니다. 7단계였던 실험 기동은 대시보드 클릭 한 번이 되었습니다.

**⓶ 노력이 한 코드베이스에 복리로 쌓입니다.** 인터페이스가 균일하니 분석·시각화 코드를 장비 간에 재사용할 수 있습니다. Janelia 필자의 표현을 빌리면, 노력이 장비마다 쪼개지지 않고 하나의 코드베이스에 쌓입니다.

**⓷ 느린 판단과 빠른 실행이 분리됩니다.** (필자의 해석) 에이전트는 결정 지점에만 들어가고 실행은 결정론적 코드가 맡으므로, LLM의 지연과 비결정성이 런타임 신뢰성 문제로 번지지 않는다고 판단됩니다.

그렇다면 이 사례들에서 에이전트는 정확히 무엇을 잘했을까요? 사람 전문가보다 물리를 더 잘 이해해서였을까요?

> ### 📌 에이전트가 이긴 곳은 "더 똑똑한 휴리스틱"이 아니라 "비싼 측정을 매번 하는 것"이었다
>
> QuEra의 PID 튜닝에서 전문가는 서보가 보고하는 RMS 오차라는 근사 지표를 믿고 튜닝합니다. 12개 파라미터를 바꿀 때마다 오실로스코프 트레이스를 떠서 푸리에 변환하는 일은 사람에게 현실적이지 않기 때문입니다. 반면 Claude는 조정할 때마다 트레이스를 캡처해 전체 스펙트럼을 계산했고, 이를 수백 번 반복해 RMS 휴리스틱이 놓친 공진을 잡아냈습니다. 복구 스크립트도 교란을 수없이 반복 주입하며 패턴을 찾은 결과입니다.
>
> 반대로 기포나 증발처럼 **물리 직관**이 필요한 곳에서는 실패하였습니다(5.3절, 7절). **정리하면 에이전트가 이기는 조건은 "빠르고 안전하게 반복할 수 있는 실험 루프 + 정량 지표"이고, MHS가 공급하는 것이 바로 그 앞부분이라고 할 수 있겠습니다.**

### 5.2 QuEra — 가장 정량적인 사례

QuEra의 중성원자 양자컴퓨터는 레이저로 원자를 제어하고, 각 레이저는 주파수를 약 1조분의 1 정밀도로 유지해야 합니다. 이 상태를 "lock"이라 부릅니다. 온도, 진동, 기압 같은 일상적 교란이 lock을 풀면 양자 연산이 실패하기 시작합니다. 드문 유형의 교란은 여전히 전문가가 여러 계기를 동시에 보며 5–10분에 걸쳐 복구해야 하고, 기계 대수가 늘면 이 방식은 버틸 수 없습니다.

**Relock.** 이전에는 레이저 엔지니어, 소프트웨어 엔지니어, 알고리즘 전문가, 테스터로 꾸린 팀이 수 개월을 들여 전용 복구 스크립트를 만들었습니다. 이 스크립트는 전문가의 수작업 절차를 단계별로 그대로 옮긴 **선형 시퀀스**였습니다. 선형 시퀀스는 중간에 교란이 들어와 이미 끝낸 단계를 되돌리면 처음부터 다시 해야 하는데, 누가 실험실 문을 열어 기압이 바뀌는 정도로도 그렇게 됩니다.

QuEra는 같은 문제를 MHS를 통해 Claude에 넘겼습니다. 목표(독립 실행되는 Python 복구 스크립트 작성)와 성공 정의(첫 시도에 relock 후 30초 유지)를 주고, 빔 차단, 계기 전원 차단, 주파수 강제 이탈 같은 교란을 유도했습니다. 그 위에서 3.4절의 4역할 루프가 밤새 돌았습니다.

속도가 곧 성공률인 이유를 간단한 모형으로 살펴보겠습니다(필자의 장난감 모형).

$$P_{\text{success}}(T) \approx e^{-\lambda T}$$

- $P_{\text{success}}$: 복구 시도 1회의 성공 확률
- $T$: 복구 시도 1회에 걸리는 시간
- $\lambda$: 이미 끝낸 단계를 되돌리는 교란의 발생률 (포아송 과정 가정)

기존 스크립트의 58%, 150초를 대입하면 $\lambda \approx 3.6\times10^{-3}\ \text{s}^{-1}$입니다. 같은 $\lambda$에서 6초짜리 시도는 약 97.8%가 되고, 개발 런에서 얻은 96%와 같은 크기입니다. 즉 성공률 상승의 상당 부분은 **교란보다 빨리 끝내기**로 설명됩니다. 다만 이 모형은 모든 실패가 교란 때문이고 교란 환경이 같다고 가정하며, 발표문으로는 이를 확인할 수 없습니다.

**속도의 원천은 구조 변화입니다.** Claude는 선형 시퀀스를 계기 판독값에 따라 분기하는 decision tree로 바꾸었습니다. 예를 들어 주파수가 조금만 움직였다면 대부분의 조정 손잡이는 효과가 없으므로 한두 개만 건드립니다. 사람이라면 확인하려고 모두 거쳐야 하는 손잡이를 건너뛰는 것입니다. 로봇 제어 용어로는 **개루프 절차를 상태 피드백 정책으로 바꾼 것**입니다.

**PID 튜닝.** lock의 품질, 즉 얼마나 자주 풀리는지는 서보 루프 안의 서로 얽힌 파라미터 12개가 정합니다. Claude는 16시간 동안 무인으로 363회 실험하며, 조정할 때마다 트레이스를 떠서 전체 스펙트럼을 확인했습니다. 독립 검증을 위해 전문가가 Claude의 결과를 보지 않은 채 처음부터 다시 튜닝했고, 두 파라미터 세트를 위상 잡음 분석기(절대 위상 잡음을 재는 특수 장비)로 비교했습니다.

| 과제 | 평가 | 결과 |
|---|---|---|
| Relock | 기존 전용 스크립트 | 58%, 시도당 약 150초 |
| Relock | 개발 런 (밤샘 개선 루프가 끝난 시점) | 96%, 약 6초 |
| Relock | blind test (에이전트 없이 완성 스크립트만, 무작위 유도 교란 700회) | **99.3%** (695/700). 단순 교란 0.9–5.4초, 최난 교란 10–14초 |
| Relock | 사람 전문가 | 5–10분 |
| PID | RMS 오차 (기존 튜닝 → Claude) | 15.7 mV → 1.55 mV |
| PID | 위상 잡음 (전문가의 새 튜닝 vs Claude) | 대역 전반 동등. 약 220 kHz 공진에서만 수동 튜닝이 약 1000배 더 많은 잡음 |
| PID | 19시간 유지 | Claude: 언락 0회 / 전문가: 시간당 약 1.6회 |

> ### ⚠️ QuEra의 헤드라인 수치는 비교 대상을 확인하고 인용해야 한다
>
> **⓵ "99.3%"와 "약 6초"는 서로 다른 평가입니다.** 약 6초는 성공률 96%였던 개발 런의 값이고, 99.3%는 에이전트 없이 돌린 blind test의 값입니다. blind test에서 어려운 교란은 10–14초가 걸렸습니다. 둘을 "58% → 99.3%, 150초 → 6초"로 한 줄에 묶으면 틀린 인용이 됩니다.
>
> **⓶ "약 10배 조용해졌다"의 비교 대상은 전문가의 새 튜닝이 아닙니다.** 10배는 **기존 튜닝** 대비이고, Claude가 최적화하던 지표인 **RMS 오차** 그 자체로 잰 값입니다. 전문가가 새로 한 튜닝과 비교하면 220 kHz 공진 한 곳을 빼고 동등합니다. 실효적 근거는 "19시간 무언락 vs 시간당 1.6회" 쪽이라고 판단됩니다.

### 5.3 Genentech — 유량 최적화, 그리고 적히지 않은 물리

BCA 단백질 정량에는 장비 셋이 필요합니다. 정밀 이송을 하는 리퀴드 핸들러, 랩웨어를 옮기는 로봇팔, 흡광도를 재는 마이크로플레이트 리더입니다. 처음에 표준 프로토콜만 주자 Claude는 물과 점성 있는 BSA 용액에 같은 유량을 썼고, BSA에서 기포가 생겨 이송량이 틀어졌습니다.

이에 폐루프 최적화를 맡겼습니다. 전문가가 정한 유량 범위 안에서 염색한 액체로 시험 이송을 하고, 흡광도를 읽어, 같은 플레이트에 있는 전문가의 이송 결과와 비교하는 방식입니다.

$$\text{RMSE} = \sqrt{\frac{1}{n}\sum_{j=1}^{n}\big(y_j^{\text{Claude}} - y_j^{\text{expert}}\big)^2}$$

- $y_j^{\text{Claude}}$, $y_j^{\text{expert}}$: $j$번째 웰에서 Claude의 이송과 전문가의 이송을 측정한 값 (발표문에 단위는 명시되지 않음)
- $n$: 비교한 웰 수

결과는 물이 약 140 µL/s (RMSE 0.016), BSA가 약 10 µL/s (RMSE 0.181)였고, 자동화 전문가들이 합리적인 값이라고 확인하였습니다. 다만 탐색 범위 자체는 전문가가 정해줬다는 점은 자율성의 범위로 기억해 둘 만합니다. 실행 중 팁 픽업 실패와 액체 감지 에러는 Claude가 스스로 복구했습니다.

**기포는 달랐습니다.** 3.2절에서 예고한 "레퍼런스에 적히지 않은 물리"가 바로 여기서 드러납니다. 혼합 중 기포로 에러가 나자 Claude의 기본 반응은 같은 웰에서 파라미터만 바꿔 재시도하는 것이었고, 액체가 더 휘저어져 기포가 늘었습니다. Claude는 에러 코드가 소프트웨어 버그가 아닌 물리적 기포에서 왔다는 것을 스스로 알아내지 못했습니다. 연구자가 "원인은 기포이고, 깨끗한 웰로 옮겨 혼합 횟수를 줄여야 한다"고 알려준 뒤에야 교정되었고, 그 뒤로는 런이 끝날 때까지 그 맥락을 유지했습니다. Genentech는 이 교훈을 재사용 가능한 액체 취급 **스킬**로 코드화해, 물성이 다른 액체에 합리적인 기본 파라미터를 고르게 했습니다. 실패하면 사람이 진단하고, 진단 결과를 텍스트로 고정하는 루프입니다.

### 5.4 CMU — 최악의 인터페이스 조합

1.1절에서 본 PC 세 대 구성에서, 원시 장비 상태부터 완성된 희석 곡선까지 약 8시간이 걸렸습니다(자율 재실행 1회 포함). 벤더에 맡기면 보통 수 주가 걸리는 작업입니다. 에이전트로는 Claude Opus 4.8을 사용하였습니다. 분주 1회는 4–5분이 걸리고, 분주량 오차가 5%를 넘으면 곡선을 쓸 수 없습니다.

워크플로 자체는 MHS 이전과 같고, 결정만 에이전트가 맡습니다. 리퀴드 핸들러가 희석 계열을 만들고, 카메라가 플레이트의 존재와 방향을 확인한 뒤에야 로봇팔이 판을 리더로 옮기고, 리더가 측정하면, 에이전트가 곡선을 보고 농도 범위를 조정해 다시 돌릴지 결과를 받아들일지 정합니다.

첫 런은 최고 농도 200 µg/mL에서 신호가 포화돼 적합도가 $R^2 < 0.9$로 나왔습니다. 에이전트는 이 판을 폐기하고, 최고 농도를 100 µg/mL로 낮춰 새 판에서 다시 돌리기로 스스로 결정했습니다. 두 번째 런은 $R^2 > 0.98$이었고, 전 과정에 사람 입력은 없었습니다. 다만 실제 약물 후보 대신 비색 염료를 대용으로 썼습니다. CMU는 장비별 드라이버를 공개할 예정이라고 밝혔습니다.

### 5.5 Tetsuwan — 하드웨어 독립 프로토콜과 컴파일러 튜닝

Tetsuwan의 ResearchOS는 자연어 프로토콜을 Claude와의 대화로 DSL 프로그램으로 바꾸고, 전용 컴파일러가 이를 자동화 코드로 내립니다. MHS를 붙이면서 프로토콜이 특정 장비에서 독립되었습니다. 프로토콜이 원심력만 지정하면, ResearchOS가 네트워크에서 호환 원심분리기를 찾아 드라이버 인터페이스를 익히고, Claude가 그 장비가 받는 단위로 변환합니다. 회전수만 받는 장비라면 변환식은 다음과 같습니다.

$$\text{rpm} = \sqrt{\frac{\text{RCF}}{1.118\times10^{-5}\cdot r}}$$

- $\text{RCF}$: 상대 원심력 (× g 단위)
- $r$: 로터 반지름 (cm)
- 원문은 이 변환을 "힘을 반지름으로 나눈다"로, 원심력을 "15,000 × rpm"으로 적었는데, 각각 위 식과 "× g"의 오기입니다

에러 처리도 확장되었습니다. 카메라가 매 이송을 찍고 CV 알고리즘이 기포와 거품을 감지하면, Claude가 연결된 장비 목록을 보고 "원료 판을 저속으로 원심분리해 기포를 제거하자"는 절차를 Slack으로 제안하고, 승인되면 실행합니다.

컴파일러 쪽에서는 폐루프 최적화를 돌렸습니다. 분주 9,143회, 전송 유형 300개, 측정 조건 1,508개에 걸쳐 트레이서 염료로 분주 정확도와 정밀도를 재고, 플레이트 리더 데이터를 MHS로 받아 컴파일러의 **정밀도 예측 모델**을 고쳤습니다. 학습된 모델은 held-out 세션에서 다중 분주 정밀도를 제조사 데이터시트보다 약 12% 더 정확하게 예측했고, 가장 많이 반복 측정한 데이터에서는 약 17%였다고 보고하였습니다. 개선된 것은 분주 정밀도 자체가 아니라, 컴파일러가 장비 배치와 팁 재사용을 결정할 때 쓰는 **예측의 정확도**입니다.

> ### ⚠️ Anthropic 발표문의 Tetsuwan 요약은 원 블로그와 두 군데서 어긋난다
>
> **⓵ 부호 검정 수치.** Anthropic 발표문은 "45회 중 31회 우세, $p \approx 0.001$"이라고 썼지만, Tetsuwan 원 블로그는 "45개 held-out 세션 중 33개, $p \approx 0.003$"이라고 밝혔습니다. 계산해 보면 원 블로그 쪽만 자기 일관적입니다.
>
> $$p = \Pr[X \ge k],\qquad X \sim \text{Binomial}(45,\ 0.5)$$
>
> - $X$: 모델과 데이터시트가 동등하다는 귀무가설 아래, 모델이 이기는 세션 수
> - $k$: 실제로 모델이 데이터시트를 이긴 세션 수
> - $k=31$ → 단측 0.008, 양측 0.016 (0.001과 맞지 않음)
> - $k=33$ → 단측 0.0012, 양측 0.0025 (원 블로그의 0.003과 일치)
>
> **⓶ 기포 복구의 자율성.** Anthropic 발표문만 읽으면 Claude가 원심분리까지 자율로 처리한 것처럼 보입니다. 원 블로그에 따르면 Claude는 판을 실러로 옮겨 밀봉하는 데까지 MHS로 수행했고, **밀봉된 판을 장비 덱 밖의 원심분리기로 옮긴 것은 Slack으로 요청받은 사람 작업자**였습니다. 에이전트는 원심분리만 실행했고, 되돌아오는 과정에도 사람 손이 들어갔습니다.

### 5.6 Janelia와 UW — 결정 지점의 에이전트

**Janelia.** 제브라피시 전신의 세포 활동을 2광자로 찍는 리그입니다. 이미징에는 속도와 커버리지의 트레이드오프가 있어, 한 평면을 빨리 찍거나 여러 평면을 느리게 찍어야 합니다. 관심 있는 진동 세포 집단을 찾으려면 커버리지가, 그 활동을 재려면 속도가 필요한데, 기존 실험은 시작할 때 한 설정을 고르고 끝까지 가야 했습니다.

Janelia 필자가 짠 에이전트 하네스는 3.4절의 패턴 그대로입니다. 획득과 분석을 번갈아 도는 **결정론적 루프**가 뼈대이고, 에이전트는 **결정 지점에만** 들어와 어느 영역을 찍을지, 어떤 분석을 돌릴지를 고릅니다. 그 결과 고정 설정이었다면 놓쳤을 진동 세포 집단을 찾았고, 반복 실험 횟수와 동물 수가 줄었다고 보고하였습니다. MHS의 원형인 Arco Bast의 리그에서는 Claude가 빔 정렬과 광학 튜닝을 맡아, 반나절 걸리던 준비 작업이 한 단계로 줄었습니다.

**UW.** 장비 6대를 드라이버 작성까지 포함해 1주 안에 연결했습니다. 이전에는 이런 통합에 수 개월에서 수 년, 수천에서 수백만 달러가 들었습니다. qPCR은 증폭 곡선이 S자로 올라가다 plateau에 들어가기 직전에 멈춰야 합니다. 에이전트가 곡선을 실시간으로 감시하다 적절한 시점에 연구자에게 중단 여부를 묻고, 중단하면 DNA 분해를 막는 4 °C 유지 단계로 넘깁니다. 로봇팔 핸드오프에서는 리퀴드 핸들러의 완료 신호를 받고 약 10초 뒤 팔이 움직였고, 반복 테스트에서 두 장비가 한 번도 충돌하지 않았습니다.

**로보틱스 관점에서 짚어두면, 여기에 학습된 조작 정책은 등장하지 않습니다.** LeRobot 기반 오픈소스 로봇팔이 하는 일은 판을 정해진 위치로 옮기는 **고정 동작**이고, 조율은 완료 이벤트를 기다리는 순차 실행입니다.

## 6. 위치잡기 — 이웃 표준들 속에서

발표문이 스스로 비교하는 대상은 MCP 하나뿐입니다. 아래 표는 기존 표준들 속에서 MHS의 위치를 잡아보려는 필자의 정리입니다.

| | ROS 2 | SiLA 2 / OPC UA LADS | MCP | MHS |
|---|---|---|---|---|
| 1차 대상 | 로봇 (센서·액추에이터) | 실험실·분석 장비 | 소프트웨어 도구·데이터 | 실험·제조 장비 전반 |
| 1차 소비자 | 로봇 제어 소프트웨어 | 스케줄러, LIMS 등 자동화 SW | LLM 에이전트 | LLM 에이전트 (+ 사람, 코드) |
| 기술 방식 | 메시지 타입, 토픽 | 기계가 읽는 기능·정보 모델 | 도구 스키마 + 자연어 설명 | 상태·절차 + 자연어 레퍼런스 파일 |
| 에이전트용 물리 맥락·안전 | 설계 목표 아님 | 설계 목표 아님 | 해당 없음 | 1급 요소 |

**기존 장비 표준은 "기계가 기계를 호출하는" 상황을 위해 설계되었습니다.** 스키마는 있지만 "이 팔은 몇 kg이라 이렇게 다뤄야 한다" 같은 조작 맥락은 담지 않습니다. 반면 MHS는 소비자가 LLM이라는 전제에서 세 가지, 즉 자연어 레퍼런스, 드라이버가 강제하는 안전 한계, 에이전트가 작성한 코드를 실행하는 경로를 1급 요소로 둡니다. Python 수준에서 하드웨어 독립 액체 취급 인터페이스를 제공하는 PyLabRobot 같은 오픈소스 라이브러리도 가까운 이웃입니다.

MHS가 SiLA 2나 LADS를 대체하는지, 그 위를 감싸는지는 발표문에 언급이 없습니다. 사례들이 COM, 파일 드롭, GUI 같은 기존 인터페이스를 아래에 두고 감싸는 방식이므로, SiLA 2 장비도 어댑터 하나로 감쌀 수 있는 구조로 보입니다(필자의 추론).

그렇다면 이름이 MCP와 짝을 이루니, MHS를 "하드웨어용 MCP 서버 모음" 정도로 이해해도 될까요?

> ### 🔗 MHS는 "MCP 서버 모음"이 아니다
>
> **MCP는 MHS에 접근하는 세 경로 중 하나일 뿐입니다.** MHS 고유의 기여는 그 아래에 있는 장비 상태 모델(공유 메모리 딕셔너리), 레퍼런스 파일, 드라이버가 강제하는 안전 한계, 그리고 코드 파일 실행 경로입니다.
>
> 생태계 쪽에서는 로봇 학습 커뮤니티의 도구 체인과 접점이 생기고 있습니다. Hugging Face가 로보틱스 라이브러리 LeRobot에 MHS 지원을 추가하고 있고, Raspberry Pi는 자사 카메라용 MHS 드라이버 테스트를 거쳐 여러 제품에 통합하고 있습니다. 하드웨어 벤더 쪽에서는 AWS(Strands Robots), Automata, Danaher, 두산로보틱스(로봇팔로 테스트 중), MBF Bioscience, QIAGEN, Tecan, Universal Robots가 지원을 준비하거나 실험하고 있습니다.

## 7. 한계 — 네 벽은 얼마나 뚫렸나

1.2절에서 이름 붙인 네 벽으로 돌아가 현재 상태를 정리합니다.

| 벽 | MHS의 장치 | 현재 상태 |
|---|---|---|
| **벽 1** 인터페이스 파편화 | 표준 드라이버 + 디스커버리 | 가장 확실히 뚫림. 다만 드라이버 작성 비용은 사라진 것이 아니라 장비당 한 번으로 옮겨졌음. UW·CMU·Tetsuwan 모두 드라이버를 직접 작성했고, Tetsuwan은 장비마다 SBC를 붙였음. 확산의 관건은 벤더의 네이티브 지원 |
| **벽 2** 코드에 없는 지식 | 자연어 태그 → 레퍼런스 파일 | 절반만 뚫림. 적힌 지식만 전달됨. 기포(Genentech), 증발(Tetsuwan: 측정된 CV의 약 1/3이 플레이트 가장자리 증발이었고, 에이전트는 증발 같은 물리 효과 추론에 애를 먹었음), 하드웨어 고장 진단(QuEra: 장비 이해가 "물리적이 아니라 프로그램적") 모두 사람이 채웠음 |
| **벽 3** 안전 | 드라이버 강제 한계 + 에이전트의 신중함 | 사례상 작동함(CMU 고장 6종 사전 차단). 다만 한계를 선언하고 검증하는 문법은 스펙 미공개로 확인할 수 없음. 소프트 층은 과잉 신중으로 실험이 밤새 멈추기도 했음(QuEra) |
| **벽 4** 시간척도 | 코드 파일 체이닝 | 개념적으로 해결됨. 다만 지연 수치가 없음. Janelia가 목표로 하는 위상 고정 광유전학 같은 폐루프 요건을 충족하는지, 공유 메모리 밖 머신 간 지연은 어떤지 기술되지 않았음 |

그 밖에 짚어둘 지점은 다음과 같습니다.

- **인터페이스 요건의 경계** — Anthropic 본문은 프로그래밍 인터페이스가 없는 장비는 아직 지원하지 않는다고 밝혔지만, CMU는 GUI만 있는 리더를 화면 조작으로 통합했습니다. 실질적인 경계는 "API도, SDK도, GUI도 없는 순수 아날로그·수동 장비"입니다. 다만 CMU도 GUI 경로에서는 결과를 검증할 수단이 화면뿐이라고 밝혔습니다.
- **평가 설계** — 모든 결과가 파트너의 자기 보고이고 비교 기준이 제각각입니다(벤더 셋업 기간, 수 개월 들인 전용 스크립트, 사람 전문가). 또한 통합 시간 단축에는 "Claude로 드라이버를 짠 효과"와 "MHS 규격의 효과"가 섞여 있어 분리할 수 없으며, CMU의 COM 드라이버가 대표적입니다.
- **맥락 공급 비용** — QuEra 팀은 원하는 결과와 수행 방법에 대해 많은 맥락을 직접 채워줘야 했습니다.
- **운용 비용과 성숙도** — 장시간 모니터링의 컴퓨트 비용이 쌓이므로, 연구자 시간 절감과 저울질해야 합니다. UW 필자 스스로 아직 PoC이며 복잡한 프로토콜은 추가 최적화가 필요하다고 밝혔습니다.

## 8. 마치며 — 이 발표가 시사하는 것

**⓵ Agentic AI 관점.** **MHS에서 가장 이식성 높은 교훈은 에이전트를 빠른 루프 밖으로 빼고, 탐색 결과를 결정론적 코드로 굳힌다는 설계입니다.** LLM 에이전트에서도 도구 호출 루프와 코드 실행 사이의 선택은 늘 있지만, 물리 세계에서는 이 선택이 지연과 비용뿐 아니라 안전과 감사 가능성까지 좌우한다고 판단됩니다.

**⓶ Physical AI / RFM 관점.** VLA가 이 스택의 어디에 들어가는지 그려보면 다음과 같습니다.

```
  LLM agent          plan, interpret, decide        (sec - min)
      |
  MHS                discover, read/write, safety limits
      |
  device procedures  e.g. arm.pick(plate)           <- a VLA could live here
      |
  device firmware    servo loops                    (us - ms)
```

**MHS는 조작 문제를 푸는 대신, 조작 위의 오케스트레이션 층을 표준화합니다.** VLA는 MHS 아래에서 "절차 제공자"로 들어갈 자리이고, LeRobot 지원이 그 연결 고리가 될 수 있겠습니다.

**⓷ 데이터 관점.** **표준화된 장비 인터페이스가 Physical AI의 데이터 병목을 풀 것이라는 기대는 절반만 맞습니다.** Genentech는 Claude의 결정을 전문가 판단과 대조하는 과정 자체가 모델 개선용 데이터셋이 된다고 명시하였습니다. 다만 MHS 로그는 에이전트의 결정 단위로 기록되는 상태·판독값 시계열입니다. 즉 "유량 → 이송 오차", "농도 범위 → $R^2$" 같은 **프로세스 수준 데이터**이며, VLA 학습에 쓰는 고주파 관측-행동 궤적과는 다릅니다. 이 때문에 RFM 데이터 파이프라기보다는 **실험 공정의 world model이나 surrogate 모델을 학습시키는 파이프**에 가깝습니다. Genentech도 실시간 데이터로 실험을 감시·최적화하는 별도 모델을 붙이겠다고 밝혔습니다. 벽 2에서 남은 기포·증발 같은 실패도 VLA가 아닌, 공정 물리를 예측하는 모델이 메울 자리로 판단됩니다.

| 용어 | 정의 |
|---|---|
| **MHS 드라이버** | OS와 장비 사이를 번역하는 표준 소프트웨어 계층. 프리미티브, 디스커버리, 레퍼런스 파일, 안전 한계를 제공 |
| **프리미티브** | 모든 장비가 이해하는 최소 명령. `read`(상태 읽기)와 `write`(상태 설정) |
| **상태 딕셔너리** | 모든 장비의 변수·제어값·센서값을 담는 공유 메모리 위의 딕셔너리. Janelia에서 기원 |
| **레퍼런스 파일** | 자연어 태그로부터 자동 생성되는 장비 설명. 측정·조정 가능 항목과 안전 한계 |
| **코드 파일 체이닝** | 드라이버 명령을 코드로 엮어 에이전트의 스텝별 추론 없이 장비 속도로 실행하는 것 |
| **하드 / 소프트 안전 층** | 드라이버가 강제하는 불변식 / 에이전트의 신중한 판단 |
| **BCA assay** | 시료의 총 단백질 농도를 흡광도로 재는 표준 정량법 |
| **qPCR** | 가열·냉각 사이클로 DNA를 증폭하며 형광으로 복제량을 실시간 측정하는 방법 |
| **lock (레이저)** | 레이저 주파수를 목표값에 초정밀로 고정해 둔 상태 |
